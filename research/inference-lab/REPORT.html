Compact state, closure, and ternary retrieval

Cloud pilot · 2026-10-24 · measured results

The pilot uses 100,000 events, 5,000 entities and 10,000 queries. All 100,000 original event records were replayed and checked. Exact queries agreed with their independent references in every repetition; 4,864,500 proof entries were checked. Approximate retrieval is evaluated separately and never authorizes state transitions.

The full fixture rebuilt closure from each of 100 snapshots, across 5 repetitions, and checked results against graph propagation. Median engine time per snapshot was 3.361 ms; the median program-write/process/engine time was 11.636 ms.

Closure theory applies to the finite positive Horn layer: extensivity, monotonicity and idempotence are checked against an independent naive evaluator. The mutable world is projected into a new snapshot before reasoning; deletion is handled by recomputation. Counts, quorum checks and missing evidence stay outside monotone inference. Closure computes consequences of known facts and rules, rather than supplying new observations. These checks establish behavior under the fixture rules, not the real-world soundness of arbitrary rules. A proof example follows a derived impact back to its source event and checksum.

The same Rust top-50 heap and avx2 instruction path are used for FP32 and INT8, with one CPU thread in each isolated worker. Over 5 repetitions, FP32 total search time divided by INT8 time was 2.30×. The resident corpus allocation was 3.98× smaller; worker peak RSS changed from 19.48 MiB to 10.32 MiB.

Across repetitions, FP32 search time ranged from 1.570 to 2.929 seconds; INT8 ranged from 0.860 to 0.951 seconds. These ranges expose the variability of this cloud run.

Queries remain FP32. INT8 codes are expanded eight values at a time in AVX2 registers (or individually in the scalar fallback); there is no full decoded corpus matrix. Positive row scales cancel in cosine similarity, so only an inverse norm per row is retained. This is mixed FP32-query/INT8-storage arithmetic, not an integer-only dot product. Search timing includes normalization, dot products and top-k selection; file loading, output serialization and query encoding are separate. The CPU counter measures scheduled thread runtime over the query loop, including result formatting/output, and excludes loading. The isolated RSS includes shared-shape query vectors and worker overhead, and excludes the Python controller and embedding model.

Native scores and top-50 membership were checked against an independent FP64 cosine oracle on 32 evenly spaced queries. Maximum observed score errors were 2.13e-07 (FP32) and 1.8e-07 (INT8), with a 2e-6 rounding tolerance. Signed-code, scalar-tail, invalid-input and stable-tie cases are covered by tests. Worker order alternates between repetitions. The NumPy table above uses four BLAS threads and a different selection routine, so it is not a matched speed baseline.

Evidence audit and next experiments

The claim register distinguishes source support, conditional claims, contradicted interpretations and unverified hardware. Key corrections: native ternary execution is not lossless conversion of arbitrary FP16 models; Maple uses eight active experts; Bonsai 27B is dense and has approximately 7.2 GB of deployed weights; PyO3 uses abi3t-py315; CPU memory bandwidth is not PCIe bandwidth; summed GPU capacities are not unified VRAM.
